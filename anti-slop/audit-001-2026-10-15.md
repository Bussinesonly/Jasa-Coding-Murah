# UI audit — 15 October 2026

Scope: source review of the React UI, responsive classes, and keyboard behavior. Production build passes. A browser preview was not available in this session, so the findings below are code-evidenced and should be visually rechecked after fixes.

## Findings

1. **HIGH — Process cards are mouse-only controls.** `src/components/Process.tsx` makes a `div` clickable and changes its selected state on mouse enter, but it cannot receive focus, communicate its selected state, or be activated with Enter/Space. This excludes keyboard users. **Rule:** R-32.

2. **HIGH — The project dialog does not manage focus.** `src/components/ProjectModal.tsx` adds dialog semantics and supports Escape, but opening it neither moves focus into the dialog nor traps focus there; closing it also does not restore the triggering card/button. Keyboard focus can move to obscured page content. **Rules:** R-26, R-32.

3. **HIGH — Mobile header controls fall below the 44 px touch target.** The theme switcher and menu button in `src/components/Navbar.tsx` use `p-2` around a 20–24 px icon, resulting in approximately 36–40 px targets. They need a 44 px minimum hit area and separation. **Rule:** R-03.

4. **MEDIUM — Portfolio cards offer two competing interactions.** A whole project card opens its detail on click while an inner “Lihat Project” button is also presented, making the nested affordance ambiguous and inviting invalid interactive nesting or duplicate activation behavior. Use one semantic control per card, or keep the card static and make the button the sole trigger. **Rule:** R-29.

5. **MEDIUM — Several published performance and delivery claims have no evidence in the UI.** Examples include Lighthouse scores, response-time figures, “100%” uptime, and finished-project metrics. These are presented as facts in hero, benefits, and portfolio mockups without a source or qualification. Replace them with verified evidence, label them as illustrative, or remove them. **Standard:** C-5.

6. **LOW — Hover treatment is not consistently reflected on focus.** Service selection and client-category emphasis is driven primarily by `onMouseEnter` and hover styling. Their click state is usable in the service list, but keyboard focus does not expose an equivalent preview/selected-state cue. Make focus and selection visibly consistent. **Rules:** R-32, R-34.

7. **LOW — The floating WhatsApp tooltip is hover-only.** `src/components/FloatingWhatsApp.tsx` reveals its explanatory text only on mouse hover. Expose it on keyboard focus too, or rely on the existing accessible name and remove the tooltip. **Rule:** R-32.

## Follow-up — fixes applied

1. Resolved: process items are now native buttons with pressed state, usable by keyboard.
2. Resolved: the project dialog now moves focus to its close control, traps Tab navigation, supports Escape, and restores focus to the originating project button.
3. Resolved: the mobile theme and menu controls now have 44 px hit areas.
4. Resolved: project cards are semantic articles; the single, explicit button opens the details dialog.
5. Resolved: unverified numerical claims and simulated production-status copy were replaced with descriptive, non-quantified copy.
6. Resolved: service selection now uses explicit click/focus interaction rather than hover activation; non-interactive client cards keep only decorative hover styling.
7. Resolved: the WhatsApp tooltip is also shown when its link receives keyboard focus.
